# GeorgePM

**从需求定义、交互原型到研发交付，一个插件、三个 Skill。**

GeorgePM 将三阶段产品工作流整理成可复用的指引和模板，面向使用 AI 辅助产品设计的产品经理、独立开发者与小团队。默认中文，跟随用户语言。首版 v0.1.0。

| 阶段 | Skill | 输入 | 输出 |
| --- | --- | --- | --- |
| ① 需求定义 | `pm-define` | 想法、项目已知信息或迭代需求 | 通过脑暴与追问收敛的 PRD、逻辑与边界、待确认项 |
| ② 交互原型 | `pm-prototype` | 已确认 PRD、设计系统或原型基线 | Demo 展示、评审原型、UI 工作任务清单 |
| ③ 研发交付 | `pm-deliver` | 最终原型、有效决议、PRD | 开发与测试交付规格，可供各岗位 AI 读取的项目资料库 |

每个 Skill 可以独立使用，也能顺序交接。阶段切换以用户授权为准；完成文档不自动意味着评审通过、服务接入或生产验收。

## 三个阶段如何协作

### 阶段一：脑暴与追问，完成 PRD

从项目已知信息出发，通过脑暴梳理想法，再围绕缺口追问，确认业务流程能否闭环、各类状态如何衔接，以及权限、异常和范围边界。已经明确的内容直接继承；尚无依据的内容保留为假设或待确认项。

这一阶段完成可评审的 PRD 需求文档，让后续设计、开发和测试依据同一份需求推进。

### 阶段二：把需求变成可体验、可评审的原型

阶段二采用下图所示的沙盒形式，围绕当前已确认范围组织三个部分：

| 部分 | 用途 |
| --- | --- |
| **Demo 展示** | 展示完整用户流程和交互反馈，便于理解产品如何使用；模拟数据与未接入服务保留标注。 |
| **评审原型** | 通过页面路由、产品画布及需求说明、测试要点、开发说明，对照界面核对规则、状态和边界。 |
| **UI 工作任务清单** | 按页面、组件、可见状态和本轮改动拆出设计工作，关联位置与需求编号，便于分工和跟进。 |

三部分服务于同一套需求与原型，保持规则、编号和变更一致；纯接口、存储或计算规则归入对应规格说明。

### 阶段三：对接开发与测试，形成 AI 项目资料库

以最终原型和已确认需求为基础，整理当前范围内的链路流程图、业务规则、状态变化、异常处置、边界定义、数据依赖、验收标准及实现差距，形成研发与测试可以使用的交付资料。默认以自包含 HTML 呈现，并保留需求、规则和验收之间的关联。

这套资料也可以作为项目的 **AI 项目资料库**：产品、设计、开发、测试等岗位可将同一版本的文档及关联资料交给各自的 AI 工具，在遇到不确定的点时，询问具体页面、流程或规则。这里的资料库是随项目交付、供人和 AI 读取的资料集合。

### 让各岗位的 AI 围绕同一份项目信息协作

设计可以询问某个状态应展示什么；开发可以核对触发条件、权限和异常分支；测试可以追问验收前置、边界值和失败后的预期表现。回答应引用对应文档、章节或需求/验收编号；资料中缺失或冲突的内容，先列为待确认，由负责人确认后回写当前资料。

向下一个岗位或 AI 工具交接时，带上当前版本、有效决议、相关编号和未决项。各方沿用同一份项目事实，减少重复解释，也便于后续 AI 工具之间传递上下文。自动连接不同工具需要另外配置；阶段三资料本身不代表生产功能已经实现或验收通过。

## 快速开始

本仓库提供 Skill 源码和兼容插件清单，尚不代表已进入任何官方插件商店。无需 API Key、MCP 服务或作者的私人环境；原型真实验证需要宿主具备浏览器工具。

### 从 GitHub 安装

仓库：[george1101-hub/GeorgePM](https://github.com/george1101-hub/GeorgePM)

Codex 添加仓库来源：

```sh
codex plugin marketplace add george1101-hub/GeorgePM
```

Claude Code 添加仓库来源并安装：

```text
/plugin marketplace add george1101-hub/GeorgePM
/plugin install georgepm@georgepm-marketplace
```

下载：[v0.1.0 发布包](https://github.com/george1101-hub/GeorgePM/releases/tag/v0.1.0)。下面保留本地安装方式。

### Codex

在支持 repo marketplace 的 Codex 环境，将下载或克隆后的仓库作为本地来源添加：

```sh
codex plugin marketplace add /absolute/path/to/GeorgePM
```

然后按当前客户端的插件入口安装 GeorgePM，并在新聊天测试。仓库提供 `.agents/plugins/marketplace.json`；具体入口与可用性取决于客户端。也可把需要的 `skills/pm-*` 目录完整复制到宿主支持的 Skill 目录，保留 `references/` 和 `agents/`。

```text
使用 $pm-define，帮我梳理一个共享会议室预约工具的需求。
使用 $pm-prototype，按已确认的 PRD 做桌面 Web 原型，仅本地演示。
使用 $pm-deliver，把这个最终原型整理为研发交付规格。
```

### Claude Code

仓库同时提供 `.claude-plugin/plugin.json` 与本地 marketplace。在支持该命令的客户端，使用完整的本地仓库路径：

```text
/plugin marketplace add /absolute/path/to/GeorgePM
/plugin install georgepm@georgepm-marketplace
```

通过技能列表选择需求定义、交互原型或研发交付，或自然语言说明当前阶段。两类客户端的打包结构有官方文档依据，首版尚未完成真实宿主安装与跨客户端端到端试用；静态校验不能证明安装成功。

[会议室预约契约走读](examples/meeting-room/README.md) 用同一条需求展示三阶段如何衔接，包含明确的模拟和待验证标记。它是文档示例，**不包含可运行预约应用、真实截图或生产实现**。

模板在各 Skill 的 `references/` 下。建议项目按 `stage1/`、`stage2/`、`stage3/` 和 `HANDOFF.md` 存放；实际路径服从用户选择。插件不创建或强制使用作者本机目录。

## 包内与边界

- 内置：分批澄清、范围继承、稳定需求 ID、覆盖表、双向组件标注要求、真实验证记录、原型到规格追溯。
- 不捆绑：私人记忆、现有业务项目源码、原始品牌与业务素材、账号、密钥、模型 SDK、外部组件库或生命周期 hooks；介绍页仅展示脱敏截图。
- 不自动执行：公开发布、真实支付、服务写入、全局安装或替用户发送消息。
- 每个阶段保留已确认、建议默认、待产品确认、待技术确认、已测与未测的区别。
