# GeorgePM · 阶段一：需求定义

把业务想法整理为可评审的现行产品契约。默认使用用户的语言；不要求安装其他 Skill、私人记忆或本机检查器。

## 建立输入与范围

读取用户提供的材料及任务目录中的交接记录。先区分全新项目或迭代：迭代写明基线文件/版本、本次变更、保留及撤销项，保留已有需求 ID。记录目标用户、主要任务、问题与成功口径、角色端、目标平台、范围边界及约束。业务角色和设备平台分别记录；员工端不自动意味着移动端，配置需求不自动意味着设计完整后台。

把信息分为：用户已确认、材料可证、建议默认值、待确认。没有证据的指标、责任人、排期和结论不补造。外部事实可能变化时查询权威来源，附实际日期和链接。

## 收敛关键决策

先找会改变范围、业务结果或验收的歧义，再提问；每批最多三个问题，给可比较的选项和理由。已回答的事项不重复确认。用户明确要求直接出稿或授权你决定时，给出建议默认值并标记待验证，不制造已确认记录；仍受外部操作权限约束。

按场景检查触发条件、前置权限、输入校验、状态转移、成功反馈、失败恢复、重复操作和撤销。只展开与本项目相关的问题。技术方案可列为建议，不把数据库、接口路径或并发实现写成产品已拍板。

## 生成评审稿

按 [PRD 模板](references/prd-template.md) 裁剪章节。每条需求具备稳定 REQ ID、来源、规则与可观察验收；埋点使用 EP ID。定义与引用分开，跨表引用已有 ID；撤销项保留 ID 和替代关系。迭代仅展开受影响内容，保留范围外基线。

正式 PRD 只写当前契约、必要待决项和前置条件；问答、访谈推演、未采纳方案另放工作记录。页面与视觉要求只写文字约束，不产出 UI、HTML 或实现代码。用户已明确授权后续阶段时交接过去，未授权不自动制作原型。

## 验证与交接

核对范围内需求有来源、有规则、有验收；检查引用无悬空、状态与权限无冲突、默认值没有冒充确认。对可机械检查的 ID/链接使用可用工具并记录结果；未执行不写通过。交接记录写当前版本、有效决策、未决项、下一步，列出证据位置。

结论区分“评审稿已生成”“用户已确认”“产品已实现”；文档完成不代表评审通过。模板中的槽位是写作提示，最终稿替换成事实，未知写明待定及影响。
